**Дата аудита:** 2 октября 2026 г.

## 1. Резюме для принятия решений

`yourCalendar` — это Telegram Mini App для ведения менструального календаря, самочувствия и общения с AI-персонажами. Сейчас проект находится на стадии **функционального прототипа / раннего MVP**, но не production-ready.

Главная пользовательская ценность уже видна: календарь, отметка периодов, расчёт цикла, дневник самочувствия, интерфейс персонажей и Telegram-аутентификация существуют. Самая законченная вертикаль — **Telegram auth → JWT → серверный CRUD периодов**.

При этом три обещанных продуктом направления пока являются прототипами:

1. **AI-чат не работает end-to-end:** frontend и backend используют разные URL, схему авторизации и формат ответа, а backend возвращает заглушку.
2. **Подписка не реализована:** доступ включается через `localStorage`, включён `DEV_MODE`, сервер не проверяет тариф.
3. **Симптомы и настройки не синхронизируются с сервером:** API-заглушки, отсутствуют модели и полноценная UI-логика.

Ключевой вывод: **сейчас не следует расширять функциональность новыми экранами**. Сначала необходимо закрыть безопасность, соединить уже созданные части в один рабочий сценарий, определить единый источник данных и добавить тестовый контур.

1. `frontend/chat.html:69` подключает отсутствующий `scripts/config.js`.
2. Frontend вызывает `POST /api/chat` — `frontend/scripts/chat.js:185`.

## 5. Основные трудности и риски

## P0 — блокирует безопасный релиз

### Секреты хранятся в локальном `.env`

Проверка без вывода значений показала, что настроены `GEMINI_API_KEY`, `BOT_TOKEN`, `DATABASE_URL` и `JWT_SECRET`. `.env` исключён через `.gitignore` и сейчас не отслеживается Git; записей о нём в доступной истории не найдено. Однако нельзя гарантировать, что значения не использовались или не передавались ранее.

**Действие:** перед публикацией перевыпустить API-ключ и bot token, сменить пароль БД и JWT-secret; создать `.env.example` только с именами переменных.

### Чат не соединён end-to-end

Это не отдельный баг, а несовместимость четырёх контрактов: файл конфигурации, URL, auth и response schema. Исправлять нужно одним вертикальным изменением с интеграционным тестом.

### Paywall обходится полностью

Клиентская проверка и `localStorage` не являются контролем доступа. До появления серверного entitlement все платные возможности должны считаться незащищёнными.

## P1 — высокий риск потери данных и проблем приватности

### Два источника истины для периодов

Приложение загружает локальные данные (`cycle-data.js:140-164`), затем после входа полностью заменяет массив серверным ответом (`index.js:299-306`). Если у нового пользователя сервер пуст, ранее введённые локальные данные исчезнут из интерфейса. Нет миграции, merge-правил и разрешения конфликтов.

### Чувствительные данные в `localStorage`

Там лежат периоды, симптомы, заметки и чаты. Для health-related продукта необходимы:

- ясное согласие;
- политика хранения;
- удаление/экспорт;
- очистка при выходе;
- минимизация данных;
- защита от XSS и сторонних скриптов.

### Широкий CORS

Текущее окружение использует wildcard `*`, а backend разрешает все методы и заголовки — `backend/api/route.py:31-44`. Для production нужно разрешить только домен Mini App.

### Нестабильная конфигурация API

`frontend/scripts/api.js:1` содержит захардкоженный временный домен `trycloudflare.com`. Нет разделения dev/staging/prod и устойчивого процесса деплоя.

### Сломанные пути к статике

CSS-файлы находятся в `frontend/styles`, но ссылаются на `fonts/...` и `backgrounds/...`, то есть браузер ищет ресурсы внутри `styles`. Требуются пути `../fonts/...` и `../backgrounds/...`.

Примеры: `frontend/styles/style.css:3,33`, `chat.css:3,29`, `profile.css:3,31`, `settings.css:3,18`. Дополнительно `backgrounds/home.jpg` отсутствует — существует `home.png`.

## P2 — качество и поддерживаемость

### Монолиты

- `backend/api/route.py` — 454 строки и одновременно config, схемы, auth, CRUD и заглушки;
- `frontend/scripts/index.js` — 775 строк и одновременно auth, API, календарь, формы и навигация;
- `frontend/styles/style.css` — около 986 строк.

Для прототипа допустимо, но подключение оплаты и AI без декомпозиции приведёт к быстрым регрессиям.

### Гонки и ограничения БД

- проверка пересечения периодов выполняется SELECT перед INSERT — `backend/api/route.py:127-147,325-349`;
- в БД уникальна только пара `(user_id, start_date)` — `backend/database/models.py:64-66`;
- параллельные перекрывающиеся интервалы могут пройти проверку;
- `IntegrityError` и rollback не обрабатываются при регистрации и создании периода;
- в БД нет CHECK-ограничений на порядок дат и максимальную длительность.

### Истечение JWT

Токен по умолчанию живёт 30 минут — `backend/api/route.py:25-27`. При 401 клиент только выдаёт общую ошибку — `frontend/scripts/api.js:29-35`. Нет прозрачной повторной Telegram-аутентификации.

### Наблюдаемость

Нет health/readiness endpoint, структурированного логирования, request ID, метрик, серверного rate limiting и централизованного error handling.

### Документация

`README.md` описывает только миграции. Не задокументированы запуск API/бота/frontend, переменные окружения, архитектура, API, тесты и деплой.

### Репозиторий

В Git отслеживаются `__pycache__/*.pyc`. Их следует удалить из индекса и добавить в `.gitignore`. Сообщения части коммитов (`ssddsada`, `Update...`) плохо объясняют изменения, что затруднит командную разработку и поиск регрессий.

## 8. План развития

## Этап 0. Security hotfix и порядок в репозитории — 1–2 дня

2. Добавить `.env.example`, расширить `.gitignore` (`__pycache__/`, `*.pyc`, виртуальные окружения).
3. Удалить `.pyc` из Git-индекса.
4. Ограничить CORS известным origin.
5. Перенести API URL в environment/config, убрать временный tunnel из кода.
6. Исправить пути CSS и отсутствующий `home.jpg`.
7. Отключить `DEV_MODE`; до готовности оплаты оставить только бесплатного персонажа.

**Критерий готовности:** в репозитории нет секретов и generated-файлов; все страницы загружают ресурсы без 404; production-конфигурация не содержит wildcard и временных URL.

**Критерий готовности:** пользователь не теряет локальные данные; один и тот же сценарий работает после перезапуска и на втором устройстве; чужие периоды недоступны.

4. Описать срок хранения и минимизацию данных.
5. Реализовать экспорт и полное удаление пользовательских данных.
6. Добавить экран согласия и политику приватности.
7. По возможности убрать медицинские записи и чаты из постоянного `localStorage`.

**Критерий готовности:** данные контролируются пользователем, удаляются и синхронизируются предсказуемо; AI получает только явно разрешённый минимум.

## Этап 5. Подписка и настройки — 5–8 дней

1. Реализовать invoice endpoint и Telegram payment flow.
2. Обрабатывать webhook идемпотентно.
3. Создать серверный entitlement и проверять его на каждом платном запросе.
4. Реализовать тему, фон, бесплатного персонажа и уведомления.
5. Синхронизировать настройки через API.
6. Добавить недостающие аватары или убрать незавершённых персонажей.
7. Удалить дублирующий `character.js`.

**Критерий готовности:** изменение `localStorage` не открывает платный чат; повтор webhook не создаёт двойную подписку; настройки переживают смену устройства.

## Этап 6. Production readiness — 3–5 дней

1. Разделить backend на routers/services/core/repositories.
2. Разделить frontend-логику на ES modules; оставить единый API client.
3. Добавить health/readiness, логирование, error tracking и метрики.
4. Настроить backup/restore PostgreSQL.
5. Добавить staging и smoke/E2E сценарий внутри Telegram WebApp.
6. Провести security и privacy review перед открытой публикацией.

**Критерий готовности:** есть наблюдаемость, восстановление, автоматический релиз и подтверждённый smoke-test ключевых сценариев.

## 9. Рекомендуемый порядок ближайших задач

1. **Не добавлять новые экраны.**
2. За один короткий PR закрыть `.gitignore`, CSS assets, config и `DEV_MODE`.
3. Вторым PR реализовать безопасную синхронизацию периодов и тесты этой вертикали.
4. Третьим PR соединить чат end-to-end без платежей, но только для бесплатного персонажа и с лимитами.
5. После стабильного чата реализовать серверные симптомы и privacy-функции.
6. Только затем добавлять реальную оплату и остальные персонажи.

Такой порядок минимизирует переделки: подписка опирается на рабочий чат, чат — на стабильную авторизацию, а авторизация — на воспроизводимый backend и тесты.

## 10. Итог

Проект уже демонстрирует идею и имеет хороший объём UI/календарной логики. Это не «пустой макет»: Telegram auth, JWT и CRUD периодов дают реальную основу. Главная проблема — не недостаток экранов, а отсутствие законченных вертикальных сценариев и инженерных гарантий.

Приоритет на будущее: **безопасность → единый источник данных → тесты → рабочий AI-чат → privacy → подписка → production-инфраструктура**. После выполнения этапов 0–3 проект можно считать технически готовым к закрытой beta; после этапов 4–6 — кандидатом на публичный запуск.
